# API каталога, свободных окон и тестовой записи

Этап 1 платформы записи. Оба маршрута используют один каталог Laravel и доступны по Bearer-ключу. `CatalogService` и `AvailabilityService` можно вызывать из будущих адаптеров с их собственным набором разрешённых филиалов.

## Запуск в Postman

1. Из корня проекта выполните `bash scripts/booking-postman.sh`. Нужны установленные Composer-зависимости и расширение PHP SQLite. Скрипт запустит Laravel на `127.0.0.1:8011`, создаст отдельную SQLite-базу с вымышленными записями и напечатает путь к приватному окружению Postman. Для другого порта передайте его первым аргументом.
2. Импортируйте [коллекцию Postman](postman/booking-integrations.postman_collection.json) и сгенерированный файл `booking.postman_environment.json`. Выберите окружение **Laravel Booking · local demo**. В нём есть отдельный ключ Postman с правами `catalog:read`, `availability:read` и второй ключ только с `catalog:read` для проверки отказа.
3. Запустите всю коллекцию через Collection Runner. Запросы проверяют код ответа, ID и контрольные значения. Для запуска из терминала используйте `npx --yes newman run docs/postman/booking-integrations.postman_collection.json -e /путь/к/booking.postman_environment.json`.
4. Используйте окружение в день запуска демо по Москве. Для нового дня запустите скрипт снова и импортируйте новое окружение. Сервер останавливается по Ctrl+C. Файлы базы и окружения лежат в напечатанном временном каталоге.

В коллекции заголовки и авторизация заданы заранее. Для ручного запроса передайте `Accept: application/json`, `Authorization: Bearer <ключ>` и для POST `Content-Type: application/json`.

## Каталог

`GET /api/integrations/v1/catalog/search` с правом `catalog:read`.

- `type` и `q` обязательны. Поддерживаются `doctor`, `branch`, `city`, `clinic`. Для врача ищем по фамилии, ФИО или специальности. Для филиала ищем по названию или адресу.
- `city_id` сужает поиск. `limit` по умолчанию равен 20, максимум 50.
- Поиск учитывает регистр, пунктуацию и `ё/е` через нормализацию. Для фамилий на `-ая` поддерживаются формы на `-ой` и `-ую`.
- Если обычный поиск ничего не нашёл, каталог ищет похожие ФИО и названия филиалов, городов и клиник в пределах доступных филиалов. Для запросов от пяти символов допускается одна правка, от восьми — две. Если найдены похожие варианты, ответ содержит `meta.approximate: true`. В голосовом диалоге при таком ответе попросите пользователя подтвердить выбор перед поиском окон, даже если вариант один.
- `meta.ambiguous: true` означает, что совпадений несколько. Уточните выбор по имени, городу или адресу. `meta.has_more` показывает, что кандидатов больше лимита.
- Примеры для вкладки **Params**: `type=doctor&q=Видлацкой` возвращает двух врачей с ID `1` и `2`, адресами филиалов в Кирове и Москве. `type=doctor&q=офтальмолог&city_id=1` возвращает ID `1, 3, 6`. `type=branch&q=Ленина 1` возвращает филиал `1`, `type=branch&q=Север` — филиал `2`.

Специальность берётся из `doctors.specialty`. Для филиала 1С при пустом поле используется последняя по ID ячейка этого врача и филиала с заполненным `doctor.espec` или `doctor_speciality`. На этапе 1 фильтр `specialty` принимает текстовое название, например `офтальмолог` совпадает с `Детский офтальмолог`. Для локальных врачей заполните поле каталога при подготовке рабочего справочника.

## Свободные окна

`POST /api/integrations/v1/availability/search` с правом `availability:read`. Тело — JSON-объект.

| Поле | Поведение |
| --- | --- |
| `city_id` | Один город |
| `clinic_ids`, `branch_ids`, `doctor_ids` | Непустые списки ID. До 20 клиник, 20 филиалов, 50 врачей |
| `specialty` | Текст специальности, полученный из каталога |
| `date_from`, `date_to` | `YYYY-MM-DD`, обе даты включительно, до 31 дня. Только `date_from` выбирает один день. Без дат ищем сегодня по часовому поясу каждого филиала |
| `time_from`, `time_to` | `HH:mm`, включительные границы начала приёма на каждый день. Можно передать любую из них отдельно |
| `patient_age`, `birth_date` | Одно из двух полей. Возраст в полных годах от 0 до 130 либо дата рождения `YYYY-MM-DD` для расчёта возраста на дату приёма |
| `limit` | От 1 до 50 окон, по умолчанию 20. `meta.has_more` показывает, что лимит обрезал выдачу |

Значения внутри списка объединяются по ИЛИ, разные фильтры — по И. Пустые списки, лишние поля, несовместимые границы и явно указанные филиалы вне выбранной клиники, города или прав клиента дают `422`.

Филиал использует свой эффективный режим расписания с наследованием от клиники. Для локального режима используются смены, длительность слота филиала и занятость в заявках. Для 1С используются статусы ячеек, время последнего обновления и локальная занятость. Ответ содержит только подходящие будущие окна активных врачей в филиалах, к которым они привязаны. Сортировка идёт от ближайшего начала, затем по ID филиала, врача и окна. Время возвращается в ISO 8601 со смещением и IANA-зоной филиала. По умолчанию оба города используют `Europe/Moscow` из настроек приложения.

| HTTP | Что получает клиент |
| --- | --- |
| `200` | `data` и `meta.schedule_status` со значением `complete` либо `partial`. В `unverified_branches` указаны филиалы и даты с непроверенными данными |
| `401` | `code: unauthenticated` при отсутствующем или неверном Bearer-ключе |
| `403` | `code: insufficient_scope`, если ключ действителен, но отсутствует право на операцию |
| `422` | Ошибки фильтров в `errors` |
| `429` | Превышен лимит запросов с IP |
| `503` | `data: []`, `meta.schedule_status: schedule_unavailable`, если для подходящих филиалов и дат нет проверяемого расписания |

Когда `data` пуст и `meta.schedule_status` равен `complete`, поле `meta.empty_reason` объясняет результат:

| `meta.empty_reason` | Что сказать |
| --- | --- |
| `no_schedule` | Для выбранного врача и филиала нет приёма на указанные даты по расписанию в приложении. При поиске без выбранного врача скажите, что по запросу нет приёма на эти даты. |
| `no_available_slots` | Приём есть, но подходящих свободных окон нет. Окна могут быть заняты, уже пройти или не подходить по времени. |

Для филиалов 1С поиск использует сохранённое расписание приложения. Отсутствие ячеек у врача за день считается отсутствием приёма. Если ячейки есть, проверяется их свежесть. Порог по умолчанию составляет 1440 минут. `BOOKING_ONEC_MAX_AGE_MINUTES` задаёт общий порог, `BOOKING_ONEC_MAX_AGE_BY_BRANCH` принимает JSON вида `{"12":120}` для настройки конкретных филиалов. При `partial` или `schedule_unavailable` поле `empty_reason` отсутствует. Сообщите, что расписание удалось проверить лишь частично или не удалось проверить вовсе.

## Проверочные запросы

Для примеров ниже день запуска — 10 ноября 2026 года. Коллекция автоматически подставляет даты из сгенерированного окружения.

### К Видлацкой сегодня или завтра, иначе ближайшее у неё

В каталоге `type=doctor&q=Видлацкой` найдите обоих кандидатов. После уточнения в демо выберите Видлацкую Анну, ID `1`.

1. `POST /api/integrations/v1/availability/search`

   ```json
   {"doctor_ids":[1],"date_from":"2026-11-10","date_to":"2026-11-11","limit":5}
   ```

   Ожидается `200`, `data: []`, `meta.schedule_status: complete`. Подходящие по датам окна заняты или прошли.

2. `POST /api/integrations/v1/availability/search`

   ```json
   {"doctor_ids":[1],"date_from":"2026-11-12","date_to":"2026-12-11","limit":1}
   ```

   Ожидается `200`, одно ближайшее окно у Анны и `meta.has_more: true`. Если пациент уже выбрал филиал, передайте тот же `branch_ids` в обоих запросах. Фрагмент `data[0]`:

   ```json
   {
     "doctor": {"id": 1, "name": "Видлацкая Анна", "specialty": "Офтальмолог"},
     "branch": {
       "id": 2,
       "name": "Север",
       "address": "ул. Московская, 2",
       "city": {"id": 1, "name": "Киров"},
       "clinic": {"id": 1, "name": "Зрение Киров"}
     },
     "starts_at": "2026-11-12T15:00:00+03:00",
     "ends_at": "2026-11-12T15:30:00+03:00",
     "timezone": "Europe/Moscow"
   }
   ```

### К офтальмологу для ребёнка 7 лет в Кирове после 15:00

Ожидается `200`. У Петровой Ирины, ID `3`, остаются три окна 11 ноября по Москве.

## Подключение к тестовому контуру

Примените миграции через `php artisan migrate`. Выдайте отдельный секрет вида `client-id.<64 hex-символа>`, используя 32 случайных байта, и передайте его клиенту по закрытому каналу. В конфигурацию Laravel помещается SHA-256 полного секрета. Пример структуры переменной окружения:

```dotenv
BOOKING_INTEGRATION_CLIENTS='{"postman":{"token_hash":"<sha256 полного секрета>","scopes":["catalog:read","availability:read"],"branch_ids":[1,2]}}'
```

Без `branch_ids` ключ действует для всех активных филиалов. Пустой список закрывает доступ ко всем филиалам. Для отзыва удалите запись клиента, для ротации замените хэш. После изменения окружения обновите кэш конфигурации, если он используется. Рабочие ключи и локальные файлы окружения Postman храните за пределами Git.

## Запись в выбранное окно на локальном контуре

1. Выполните `bash scripts/booking-postman.sh 8011 8012`. Laravel слушает на `127.0.0.1:8011`, имитатор 1С — на `127.0.0.1:8012`. Скрипт создаёт временную SQLite-базу с вымышленными пациентами и печатает путь к приватному окружению Postman. Для нового прогона перезапустите скрипт.
2. В Postman нажмите **Import** и импортируйте [коллекцию Laravel Booking · test write](postman/booking-write.postman_collection.json) и напечатанный файл `booking.postman_environment.json`. В списке окружений выберите **Laravel Booking · local demo**.
3. Откройте коллекцию и нажмите **Run**. В **Run type** выберите **Functional → Local**, затем нажмите **Start run**. Коллекция ищет три окна у Видлацкой Елены в тестовом филиале 3 и передаёт возвращённые предложения в следующие запросы. [Postman Collection Runner](https://learning.postman.com/latest-v-12/docs/tests-and-scripts/running-collections/intro-to-collection-runs).
4. Ожидаемые ответы по порядку — поиск `200`, создание `201 confirmed`, статус `200 confirmed`, повтор `200` с тем же `booking_id`, занятое окно `409 slot_unavailable`, затем три ответа `202 unknown` на неполный ответ 1С, проверку статуса и повтор.

Для запуска из терминала:

```sh
npx --yes newman run docs/postman/booking-write.postman_collection.json -e /путь/к/booking.postman_environment.json
```

### Контракт записи

[OpenAPI](booking-write.openapi.yaml) описывает создание и проверку статуса. Запись открывается только для филиалов, указанных и в `BOOKING_WRITE_BRANCH_IDS`, и в `branch_ids` клиента. По умолчанию список включённых филиалов пуст. Демо выдаёт отдельный Bearer-ключ с правами `availability:read`, `bookings:write`, `operations:read` и доступом к филиалу 3. Окна `onec_push` для этого ключа содержат `offer_token` и `offer_expires_at`. Предложение привязано к клиенту и действует 10 минут.

- В **Headers** запроса `POST /api/integrations/v1/bookings` передайте `Idempotency-Key` со значением UUID v4, созданным при подтверждении. В **Body → raw → JSON** передайте `offer_token`, `full_name`, `birth_date` в формате `YYYY-MM-DD`, `phone`, при наличии `full_name_parent`, а также `confirmed: true` и `privacy_consent: true`. Эти поля фиксируют полученные подтверждение и согласие.
- После потери ответа выполните `GET /api/integrations/v1/operations/{id}` с тем же Bearer-ключом, подставив в `{id}` значение исходного `Idempotency-Key`. Если операция ещё не найдена, повторите создание с исходным телом и тем же ключом. Для уже принятой операции повтор работает и после истечения предложения.
- `confirmed` означает подтверждённую запись. `slot_unavailable` означает, что нужно заново поискать время. `unknown` означает, что исход не установлен. Laravel сохраняет UUID для сверки и блокирует повторную отправку по той же операции и запись в пересекающееся окно через этот API.

## Одна ручная проверка на adminzrenie.ru

1. После выкладки и миграции добавьте на сервере `BOOKING_WRITE_BRANCH_IDS='[8]'`, если выбран филиал 8. В существующий JSON `BOOKING_INTEGRATION_CLIENTS` добавьте отдельного клиента `postman-write`, сохранив текущих клиентов. Используйте ID выбранного филиала в обоих списках. Обновите конфигурацию командой `php artisan config:cache`.

   ```json
   {"postman-write":{"token_hash":"<sha256 полного токена postman-write.…>","scopes":["availability:read","bookings:write","operations:read"],"branch_ids":[8]}}
   ```

2. Нажмите **Import** и выберите [коллекцию для ручной проверки](postman/booking-write-production.postman_collection.json). В **Environments** задайте локальные значения `write_token`, `branch_id`, `doctor_id`, `appointment_date` (`YYYY-MM-DD`). Откройте **1. Find an available window** и нажмите **Send**. Проверьте врача, адрес и время, затем скопируйте `offer_token` нужного окна в одноимённую переменную.
3. Задайте `operation_id` как новый UUID v4. Введите данные для теста в `test_full_name_json` (имя в двойных кавычках как JSON-строка), `test_birth_date` (`YYYY-MM-DD`) и `test_phone` (`+7` и 10 цифр). Откройте **2. Create one test booking** и нажмите **Send** один раз. В запрос уже включён комментарий `ТЕСТ. Не связываться.` Он передаётся в 1С. При `201 confirmed` проверьте запись. При `202 unknown` откройте **3. Check the same operation** и нажмите **Send**. Для проверки повтора используйте то же тело и тот же `operation_id`.
4. Отмените тестовую запись штатно через админку и проверьте отмену в 1С. Если исход `unknown`, найдите запись в 1С по врачу и времени перед повторной попыткой. Для ElevenLabs после проверки выдаётся отдельный ключ со своим списком филиалов.

## Голосовая проверка в ElevenLabs

На `adminzrenie.ru` клиент `elevenlabs-pilot` имеет права `catalog:read`, `availability:read`, `bookings:write` и `operations:read`. Его `branch_ids` и серверный список записи включают восемь филиалов «Ангелов зрения» (`clinic_id=2`, IDs `6, 8, 9, 10, 11, 12, 18, 19`). Ключ хранится в ElevenLabs как Secret `adminzrenie_booking_pilot` со значением `Bearer <ключ>`. На сервере в конфигурации хранится хэш ключа.

У агента **Тест расписания** на ветке **Main** подключены четыре Webhook Tools. В **Tools → Headers → Authorization** используйте **Type → Secret** и `adminzrenie_booking_pilot`. Пилотный ключ проверен на поиске окон и записи. Для `search_catalog` ещё нужно сверить выбор этого же Secret в интерфейсе агента. Он ограничивает каталог филиалами пилота. [Настройка Webhook Tools](https://elevenlabs.io/docs/eleven-agents/customization/tools/webhook-tools).

| **Name** | **Method** | **URL** |
| --- | --- | --- |
| `search_catalog` | `GET` | `https://adminzrenie.ru/api/integrations/v1/catalog/search` |
| `search_slots` | `POST` | `https://adminzrenie.ru/api/integrations/v1/availability/search` |
| `create_booking` | `POST` | `https://adminzrenie.ru/api/integrations/v1/bookings` |
| `get_booking_status` | `GET` | `https://adminzrenie.ru/api/integrations/v1/operations/{operation_id}` |

В **Description** инструмента `create_booking` вставьте «Создаёт запись на выбранное окно после явного согласия пациента на запись и на обработку данных». В **Body parameters** добавьте параметры с **Value Type → LLM Prompt**:

| **Identifier** | **Data Type** | **Required** | **Description** |
| --- | --- | --- | --- |
| `offer_token` | `string` | да | Точный токен выбранного окна из последнего результата search_slots. |
| `full_name` | `string` | да | Фамилия, имя и отчество пациента, если есть. |
| `birth_date` | `string` | да | Дата рождения пациента в формате YYYY-MM-DD. |
| `phone` | `string` | да | Контактный номер в формате +7 и десять цифр. |
| `full_name_parent` | `string` | нет | ФИО родителя или представителя, если сообщено. |
| `confirmed` | `boolean` | да | true после явного подтверждения выбранного врача, адреса, даты и времени. |
| `privacy_consent` | `boolean` | да | true после явного согласия на обработку данных для записи. |
| `comment` | `string` | нет | Для согласованного теста передай «ТЕСТ. Не связываться.». |

Для `get_booking_status` в **Description** вставьте «Проверяет исход уже отправленной записи». В **Path parameters** задайте `operation_id` типа `string`, **Value Type → LLM Prompt**. Описание поля «UUID выбранного окна из search_slots или ответа create_booking для этой же попытки».

### Как продолжить проверку

1. В **Agent → System prompt** сверить опубликованный текст. В **Tools → search_slots → Body parameters** сверить, что фильтры врача и филиала можно опустить, а `date_to` доступен для поиска диапазона.
2. Когда появятся кредиты, открыть **Preview → New conversation**. Проверить отдельными разговорами «Какие врачи свободны завтра на Преображенской, 38?», «Найди ближайшее окно у Видлацкой» и запросы «послезавтра» и «на 22-е». В **View details** сверить реальные параметры и ответы инструментов. При проверке поиска достаточно дождаться списка окон.
3. Для сквозной проверки другого филиала использовать согласованную тестовую запись и после успеха отменить её в админке. На Эйзенштейна, 6, запись через Postman и голосом уже прошла на 15 ноября в 15:00. Пользователь сообщил, что обе тестовые записи удалены.

Если `create_booking` получил ID формата `onec:…` вместо `offer_token`, проверьте ответ `search_slots` и Secret. Если пришёл `409 slot_unavailable`, сверяйте конкретную операцию и состояние 1С. Предыдущая операция `unknown` может блокировать интервал, даже когда календарь показывает свободное окно. Такой случай уже был на 15 ноября в 16:00, позже расписание 1С показало занятость. Исход старой операции не подтверждён.

### Что подтверждает 1С

Виджет сайта отправляет `POST /api/v1/applications` и показывает успех после ответа Laravel. При активном endpoint Laravel вызывает `bookSlot` (`bookslot`) или ручную запись (`newrecord`). Старый путь через `OneCBookingService::book` может принять JSON без статуса и использовать отправленный UUID вместо полученного ID. `bookDirect` требует возвращённый `claim_id` или `appointment_id`, но тоже допускает отсутствие статуса. В действующем HTTP-клиенте 1С отсутствует метод проверки результата по отправленному UUID.

В API записи успех требует HTTP `200` или `201`, явный `status` со значением `success`, `booked` или `confirmed` и непустой `claim_id` или `appointment_id` в ответе. Для отказа по занятости имитатор возвращает HTTP `409` с `code: slot_unavailable`. Эти признаки нужно сверить с ответами 1С. Проверка статуса читает сохранённый исход в Laravel. Операции `unknown` требуют сверки в источнике и автоматически не переотправляются. API сохраняет подтверждённую заявку без рассылок Laravel.
