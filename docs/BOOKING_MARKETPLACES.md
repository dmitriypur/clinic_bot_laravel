Подключаем онлайн-запись для всех филиалов клиники «Ангелы зрения» в Кирове и Москве. Новые города должны добавляться настройкой филиалов. Запуск на одном тестовом филиале нужен для проверки перед расширением на всю сеть.

| **1. Яндекс.Медицина** | Сначала пробуем МедФлекс. Прямое подключение к Яндексу рассматриваем, если вариант через МедФлекс не подходит. | МедФлекс описывает интеграцию «Лиды от Яндекса». ## Возможная задача: обновлять данные площадок из одной точки

По пониманию пользователя, часть данных уже выгружается из 1С, а часть сотрудники меняют вручную. Какие именно данные и на каких площадках — пока неизвестно. Цены прозвучали как предположение. Возможная цель руководителя — вносить изменение один раз и автоматически передавать его на нужные площадки. Под «ботом» в разговоре пользователь имеет в виду `adminzrenie.ru` как предполагаемую точку управления.

Предложение пользователя: сотрудники меняют данные в 1С, `adminzrenie.ru` получает изменения и автоматически отправляет их на площадки через соответствующие интеграции. Обратный поток записей предполагается через то же приложение. Роль `adminzrenie.ru` в каждом из потоков ещё нужно подтвердить у руководителя. До составления ТЗ выяснить на одном конкретном примере, что сейчас приходится менять вручную и где должно появиться обновление.

Уточнённые сценарии для Яндекс.Медицины: новый врач в 1С появляется у нужного филиала в Яндексе, изменения данных врача и цены приёма обновляют существующее предложение, снятие врача с приёма прекращает публикацию предложения для этого филиала. Отсутствие свободных окон не означает снятие врача. Для этого обмена нужен список активных врачей по филиалам и цены по врачу, услуге и филиалу из 1С. Публичный API виджета для филиалов 1С показывает врачей с будущими свободными окнами: им можно проверять наличие записи, но нельзя считать его полной выгрузкой врачей или использовать как сигнал удаления.

## Предлагаемая схема — ждёт подтверждения руководителя

**1С хранит актуальное расписание и подтверждает запись. `adminzrenie.ru` — общий узел для сайта, бота, админки и внешних площадок.** Адаптер каждой площадки преобразует данные между её форматом и внутренним форматом приложения. Вместо двух отдельных интеграций для первых площадок хотим сделать один адаптер МедФлекса, если он поддерживает подключение нашей программы в таком направлении:

- Данные клиники: **1С → adminzrenie.ru → интеграция площадки → площадка**. Для первых двух площадок таким маршрутом может быть МедФлекс. Какие именно данные кроме расписания нужно передавать, ещё предстоит уточнить. Для привязки используем стабильные идентификаторы врача и филиала.
- Запись: **площадка → МедФлекс → adminzrenie.ru → 1С**. Результат возвращаем по обратной цепочке. Запись считаем подтверждённой после явного успеха в 1С. При занятом времени предлагаем выбрать другое окно.

В приложении уже есть получение расписания из 1С, каталог, поиск окон, защищённый API записи и проверки её статуса. Цены из 1С в админку пока не приходят. Для передачи расписания и цен в МедФлекс и получения записей предусмотрен [API МИС v2](https://developer.medflex.ru/mis-api/). Адаптер ещё предстоит реализовать и подключить.

## Если МедФлекс подключается только к 1С

Если МедФлекс подтвердит поддержку конкретной конфигурации 1С клиники, можно запустить **площадка → МедФлекс → 1С**. Тогда `adminzrenie.ru` получает из 1С обновлённое расписание и сведения о созданных, изменённых и отменённых записях. Имеющиеся вебхуки расписания и событий записи дают основу для обратного обмена. Нужно проверить на реальных форматах обмена, какие события 1С отправляет по записям МедФлекса, хватает ли их для журнала админки и можно ли сохранить источник записи. Обновление занятости закрывает окно, а для появления записи в журнале нужны сведения о самой записи.

Проверка двух разных рисков:

- **Два пациента претендуют на одно время.** Правило должно действовать в 1С для всех путей записи, включая МедФлекс, сайт и ввод сотрудником в 1С. При одновременных запросах на один интервал с вместимостью один 1С проверяет и занимает время как одну операцию. Проверка расписания перед запросом и блокировки Laravel охватывают лишь часть сценариев. Если оба запроса подтверждаются, исправление требуется на стороне 1С.
- **Один запрос пришёл повторно.** Повтор одного и того же запроса или уведомления должен вести к той же записи. Для этого сопоставляем устойчивые внешние идентификаторы и сохраняем результат операции. При потере ответа 1С сначала сверяем, создалась ли запись, и только потом решаем, можно ли повторять запрос.

У одного филиала на одной площадке должен быть один активный маршрут записи и один источник публикации расписания. При выборе МедФлекса сначала проверяем наличие прямого фида Яндекса и правила перехода в инструкции «Лиды от Яндекса».

**Пауза с 20 ноября.** Григорий подтвердил, что данные сейчас идут из 1С на ПроДокторов. На вопрос о том, какой результат нужен от доработки, он предложил пока отложить задачу. Разработку и настройку не начинаем. При возобновлении сначала уточнить цель клиники и ожидаемый результат, затем выбрать схему.

**Точка продолжения.** Пользователь уточнил задачу для первых двух площадок. Расписание идёт из 1С через `adminzrenie.ru` и МедФлекс в Яндекс.Медицину и ПроДокторов, записи с обеих площадок идут через МедФлекс и админку в 1С. Начинаем с Яндекса. Формальное ТЗ клиники ещё не подтверждено. Проверены документация, ключ и локальная имитация. Адаптер ещё не добавлен.

По словам руководителя, у «Ангелов зрения» есть договор с МедФлексом и обмен с 1С, а из площадок записи приходят только с ПроДокторов. Программист 1С подтвердил работу с МедФлексом. При предыдущем подключении менеджер направил команду 1С к документации API. Детали рабочего обмена пока не проверены.

**Сообщение, пересланное Григорием 20 ноября.** Григорий переслал чужой ответ со скриншотом. Автор и исходный вопрос в имеющемся фрагменте не указаны. В ответе сказано, что выгрузка расписания и цен уже настроена и для Яндекс.Медицины потребуются настройки на стороне Яндекса. Пользователь уточнил, что действующая выгрузка идёт мимо `adminzrenie.ru`, предположительно из 1С напрямую в МедФлекс. Точный маршрут и охват филиалов не проверены. Тестовую клинику и направление записей на наш адрес не подтвердили. На присланном скриншоте открыт раздел «Дополнительные сервисы» с названием «Дом здорового зрения» в шапке. По нему нельзя подтвердить настройки «Ангелов зрения». Саму задачу клиники пользователь уже попросил Григория уточнить.

Указанная в ответе [инструкция «Интеграция с другими сервисами»](https://help.medflex.me/integraciya-cherez-api-so-storonnimi-servisami/) объясняет, как выдать ключ стороннему сервису для вызовов API МедФлекса. Этот ключ охватывает все филиалы и не настраивает отправку записей на адрес админки. Для подключения Яндекса есть отдельная [инструкция «Лиды от Яндекса»](https://help.medflex.me/lidy-ot-yandeksa/). Действующую выгрузку расписания и цен сохраняем до согласования пилота и проверки маршрута. Пока проверяем только возможность работы с отдельной тестовой клиникой или другим изолированным тестовым контуром.

В публичной [карточке Оксаны Пономаревой в Яндекс.Медицине](https://yandex.ru/medicine/doctor/ponomareva_oksana_xR5uYv24u7XQ5) уже есть ссылка на виджет МедФлекса для филиала на Ленина, 191 в Кирове. Наличие ссылки подтверждает маршрут перехода, но не подтверждает успешное поступление записей из Яндекса в 1С.

Публичная сверка 16 ноября: API виджета вернул 8 филиалов и 28 пар «филиал — врач с будущими свободными окнами». В Яндекс.Медицине найдены совпадения в обоих городах. Например, на Преображенской, 38 в API шесть врачей, а в [публичной карточке филиала](https://yandex.ru/medicine/clinic/angely_zreniya_239565058921) перечислены трое из них. Это частичная сверка по публичным карточкам. Она не показывает, где заведены данные, как выгружаются и какие цены сейчас действуют в 1С. Источник и состояние выгрузки нужно проверить в кабинетах.

**API и ключ.** В [спецификации API МИС v2](https://mis-api.medflex.ru/v2/schema?format=json) описаны оба направления обмена. Админка отправляет расписание через `POST /v2/doctors/send_schedule/`. Занятость отдельных окон обновляется через `POST /v2/occupied_doctor_schedule_slot/`. Для услуг и цен есть `POST /v2/services/send_schedule/`.

МедФлекс вызывает защищённые адреса админки для проверки доступности записи, создания записи к врачу, запроса статуса, изменения и отмены. Запрос на создание содержит идентификаторы филиала и врача, время, данные пациента и источник. После подтверждения в 1С админка возвращает `claim_id` для дальнейших операций. Для изменения записи текст спецификации указывает HTTP `200` с `status_code: 204` в теле, а таблица ответов указывает HTTP `204`. Ответ нужно сверить при интеграционной проверке.

Ключ программиста хранится в локальном `.env` как `MEDFLEX_MIS_TOKEN`. Он принят кабинетом расписания и прошёл авторизацию на методах выгрузки v2. Привязку к нужным филиалам и фактическую выгрузку с этим ключом пока не проверяли. Для вызовов админки используется отдельный ключ. [Кабинет расписания](https://mis-api.medflex.ru/login/).

**Яндекс.** «Лиды от Яндекса» ведут в виджет МедФлекса для выбранного врача. В основном кабинете включают «Лиды от Яндекса» и «Ссылку на врача», выбирают врача с настроенной записью, специальностью и ценой на ПроДокторов. Филиал сопоставляют с карточкой организации в Яндексе. У МедФлекса также есть отдельная интеграция для передачи профилей врачей. [Онлайн-запись из Яндекса](https://help.medflex.me/lidy-ot-yandeksa/) · [Выгрузка профилей](https://help.medflex.me/vygruzka-vrachyay-v-yandeks/).

**Проверка.** В локальном тесте с имитацией МедФлекса сформировали выгрузку расписания одного врача, сохранили пробную запись через API Laravel и проверили, что повтор не создал дубль, а окно закрылось. На `test.adminzrenie.ru` отключена 1С. Стенд подходит для проверки адаптера с имитацией или отдельным доступом МедФлекса. Сквозную проверку с живым расписанием провести на `adminzrenie.ru` по согласованию с клиникой. Предварительный вариант для одного врача — Преображенская, 38. [Описание стенда](../setup-deploy.md).

**Следующий шаг.** Подготовить адаптер по контракту после подтверждения ТЗ. Для подключения МедФлекс просит передать адреса приёма записей и ключ для вызова этих адресов. Инструкции для отдельных МИС указывают технический контакт `it@medrocket.ru`, название и ИНН клиники, а в некоторых случаях ID филиала. Кабинет показывает обмен по филиалам. В публичных инструкциях не описано, как поменять адрес для одного филиала при действующем обмене с 1С. Перед включением техническая команда МедФлекса должна проверить привязку ключа, филиала и нового адреса. Отдельный тестовый доступ для этой связки пока не подтверждён. [Подключение МИС](https://help.medflex.me/medicalcrm/) · [Пример с ID филиала](https://help.medflex.me/element/) · [Кабинет МедФлекса](https://help.medflex.me/obzor-lichnogo-kabineta/).

Техническую подготовку и проверки на стороне админки ведёт Codex. Перед подключением он готовит точные адреса приёма записей, ключ для этих адресов и одну инструкцию с нужными действиями на стороне МедФлекса. Григорий выполняет эти действия в кабинете и при необходимости передаёт данные техкоманде МедФлекса. Для продолжения нужно подтверждение, что для согласованного филиала подключён новый адрес. Дополнительные данные запрашивать только при необходимости, например ID филиала, если его не удалось сопоставить, или ключ выгрузки, если потребуется отдельный. Доступ к кабинету для пользователя не запрашивать.

**Что сохранить для нового чата.** Записывай здесь ссылки на проверенные разделы документации, результаты проверок и открытые вопросы. Если клиника получит тестовый доступ, добавь порядок подключения и идентификаторы тестовых филиалов. Ключи храним в настройках тестового окружения, вне документации и Git.

## Что делать после проверки контракта

1. **Выбрать маршрут и закрепить контракт.** Сверить в кабинете текущий обмен по филиалу, сопоставить идентификаторы филиала и врача и согласовать с МедФлексом адреса для приёма записей.
2. **Подготовить адаптер или обратный обмен с 1С.** Переиспользовать имеющиеся сервисы каталога, поиска и записи. Сопоставить филиалы, врачей и услуги. Обработку статусов, повторов, отмен и сверки строить на подтверждённых возможностях площадки и 1С.
3. **Проверить обмен.** Проверить повтор, отмену, одновременные запросы на одно время и потерю ответа с имитацией или на стенде при наличии отдельного доступа. Для сквозной проверки согласовать филиал и врача, проверить показ живого расписания в Яндексе, создать пробную запись через виджет и убедиться, что она появилась в 1С через админку и окно закрылось. Затем отменить пробную запись и проверить освобождение окна.
4. **Запустить и расширить.** После успешной проверки включить первый канал на согласованном филиале, затем подключить остальные филиалы Кирова и Москвы. Зафиксировать, как добавлять новые города. Подключать следующие площадки по одной, используя тот же модуль записи.
