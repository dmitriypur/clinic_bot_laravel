## 1. Решение и границы

Развивать текущее Laravel-приложение как модульный монолит. Внутри приложения выделить общий модуль каталога, доступности и записи. Сайт, ElevenLabs, админка и адаптеры медицинских площадок вызывают одну бизнес-логику записи. Каждая интеграция переводит свой формат в общий формат приложения.

Первый подключаемый новый канал — ElevenLabs. Сразу проектировать модель данных с несколькими каналами, услугами и ценами. Реализовывать и вводить изменения по этапам, с проверкой совместимости действующего виджета.

Отдельный Laravel-сервис сейчас добавит ещё одну БД, сетевую границу и необходимость согласовывать состояния. Выделение модуля в сервис рассматривать при измеренной потребности в независимом масштабировании или развёртывании. Доступ к БД модуля из будущих адаптеров не должен заменять его публичные операции.

Универсальность означает общие понятия и операции. У площадок остаются разные протоколы, сроки обновления и условия подключения. Гарантию отсутствия двойной записи можно принять только после проверки фактического механизма 1С.

## 3. Источники данных

| Данные | Кто принимает окончательное решение | Что хранит Laravel |
| --- | --- | --- |
| Расписание и запись филиала `onec_push` | 1С/МИС | Проекция расписания, операции записи, связи с внешними ID |
| Расписание филиала `local` | Laravel | Смены, ограничения ресурсов и подтверждённые записи |
| Врачи, филиалы, специальности | Назначенный владелец каждого поля | Нормализованный каталог и происхождение данных |
| Услуги, длительность, стоимость | Согласованный каталог 1С или другой действующий источник | Версионированные предложения с периодами действия |
| Описание, фото, тексты | Согласованный редакционный источник | Публикуемые сведения без перезаписи медицинских ограничений |

Эффективный режим определяется для филиала с наследованием от клиники. Нельзя автоматически переключать филиал 1С в локальное бронирование при недоступности 1С.

Для разных баз 1С внешние ID всегда ограничиваются конкретным подключением. Сопоставление врача по ФИО может дать кандидата для проверки оператором, но не должно автоматически объединять людей или выбирать получателя записи.

| Сверка | Восстановление неопределённых операций и расхождений с 1С |

Общие сервисы принимают типизированные команды и контекст авторизованного клиента. Контроллеры не вызывают друг друга. Новый модуль записи не должен дублировать алгоритмы существующих контроллеров.

Сохранение контракта сайта не означает сохранение всех внутренних алгоритмов. Старые маршруты должны вызывать общее ядро. В клиенте сайта потребуется добавить устойчивый ID намерения записи: создать один раз при подтверждении формы, использовать при сетевых повторах и сохранять до установления результата. Его можно передавать дополнительным заголовком без изменения существующих полей формы. Само серверное проксирование не даёт идемпотентности, если прокси генерирует новый ID на каждый повтор.

Существующий виджет не считать готовым к `202` без проверки. До обновления клиента адаптер старого API отображает неопределённый исход через совместимый формат ошибки с понятным сообщением и ссылкой на операцию для технической сверки. Обновлённый клиент сохраняет операцию и проверяет её результат. В обоих случаях повтор с тем же намерением не создаёт новую запись. Тексты и поведение ошибки проверяются на действующем компоненте формы до выкладки.

## 5. Поиск по всем филиалам и врачам

Пациент может указать врача, адрес, специальность, дату, период, время суток, возраст или бюджет. Помощник извлекает условия, уточняет неоднозначности и передаёт структурированный запрос. Laravel ищет в каталоге и расписании.

Правила поиска:

1. Поддерживать сочетания `city_id`, `clinic_ids`, `branch_ids`, `doctor_ids`, `specialty_ids`, `service_id`, `date_from`, `date_to`, `time_from`, `time_to`, `patient_age` или `birth_date`, `price_max`.
2. Поля внутри одного списка объединять по ИЛИ, разные фильтры — по И. Пустой переданный список и несовместимые параметры возвращают ошибку валидации. Пропущенный фильтр означает все разрешённые клиенту объекты.
3. Адрес и ФИО сначала разрешать через каталог. При нескольких совпадениях возвращать кандидатов с городом и адресом. Не выбирать произвольного врача при неоднозначности.
4. Учитывать активность врача, филиала и предложения, связь врача с филиалом, специальность, возраст, тип приёма и длительность услуги. Возраст по дате рождения считать на дату приёма. Возраст в годах достаточен для предварительного поиска; пограничные случаи требуют даты рождения и повторной проверки при записи.
5. Хранить моменты времени в согласованном UTC-представлении, а пользователю возвращать ISO 8601 со смещением и часовым поясом филиала. Проверить фактическую сериализацию уже существующих `onec_slots` до преобразований. Для Москвы и Кирова исходное предположение — `Europe/Moscow`; хранение зоны филиала предусмотреть явно.
6. Временной фильтр относится к началу приёма в каждом выбранном дне. В MVP `time_to >= time_from`; ночной диапазон разбивается на два запроса. Диапазон дат включительный.
7. Возвращать только интервалы, в которые помещается услуга. Несколько ячеек можно объединять в один приём только при подтверждённой поддержке такого бронирования источником.
8. Показанное окно не является бронью. Ответ содержит время актуальности, версию предложения и непрозрачный `offer_token`, связывающий ресурс, интервал, услугу и версию условий. Токен не является секретом доступа и не заменяет повторную проверку доступности.
9. Вводить ограничение свежести отдельно для каждого подключения. Устаревшее расписание означает `schedule_unavailable`, а не достоверное отсутствие свободного времени. Для поиска по нескольким филиалам явно показывать непроверенные филиалы.
10. Кэш выдачи изолировать по клиенту/правам, фильтрам и версии расписания. Обновление занятости инвалидирует соответствующие выборки. Перед записью не доверять кэшу.

Предлагаемые стартовые лимиты, подлежащие проверке нагрузкой: период до 31 дня, до 50 врачей и 20 филиалов в фильтре, страница до 50 окон, batch до 10 поисковых запросов. Ответ содержит `has_more` и курсор, чтобы ограничение выдачи не воспринималось как полное расписание. Сортировка по началу, филиалу, врачу и ID обеспечивает устойчивый порядок; при смене версии выдачи предложить обновление поиска.

Один поиск по нескольким врачам уже является массовой выборкой. Отдельный batch нужен для нескольких независимых вопросов. Реализовать его после основного поиска, с общим бюджетом нагрузки и отдельным результатом/ошибкой для каждого элемента. Массовое создание записей в batch не включать.

## 6. Услуги и цены

Цена принадлежит предложению услуги в филиале, при необходимости — у конкретного врача и для типа приёма. Хранить сумму в минимальных денежных единицах, валюту, точность (`exact`, `from`, `unknown`), начало/конец действия и источник. Неизвестная цена не равна нулю.

Фильтр верхней границы бюджета применяется только к сопоставимому предложению с известной точной ценой. Цена «от» не гарантирует попадания в бюджет. При изменении цены после выбора вернуть `price_changed` с новыми условиями и запросить новое согласие. В подтверждённой записи сохранять снимок согласованных услуги и цены; юридическую/операционную обязательность цены согласовать с клиникой.

В текущей модели врача нет нормализованного поля специальности: часть данных может приходить в `source_payload` расписания. До обещания поиска по специальности требуется заполнить и проверить справочник соответствий. Для голосового пилота можно включить проверенные специальности и услуги; неизвестные данные обозначать явно.

## 7. Предлагаемый API для интеграций

Новый префикс — `/api/integrations/v1`. Это проект контракта, окончательный OpenAPI создаётся до реализации эндпоинтов и проверяется контрактными тестами.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /catalog/search` | Найти города, филиалы, врачей, специальности и услуги; ограниченная выдача кандидатов |
| `GET /offers` | Условия, длительность и цена услуги в выбранном филиале/у врача |
| `POST /availability/search` | Поиск окон по сочетанию фильтров |
| `POST /availability/batch` | Несколько независимых поисков с ограничениями |
| `POST /bookings` | Создать запись на выбранное предложение |
| `GET /operations/{id}` | Узнать исход ранее принятой операции |
| `GET /bookings/{id}` | Прочитать разрешённую клиенту запись |
| `POST /bookings/{id}/cancel` | Отменить запись с отдельным ключом идемпотентности |

Создание принимает `offer_token`, необходимые данные пациента и законного представителя, факт подтверждения выбора и `Idempotency-Key`. Сервер самостоятельно определяет филиал, врача, услугу, время и 1С по предложению. Источник запроса определяется по авторизации, а не по произвольному `source` из тела запроса. Флаг согласия агента фиксирует действие в диалоге, но сам по себе не заменяет необходимые клинике согласия на обработку данных.

Пример поиска, все ID условные:

```json
{
  "branch_ids": [12],
  "specialty_ids": [3],
  "date_from": "2026-11-25",
  "date_to": "2026-11-30",
  "time_from": "13:00",
  "time_to": "18:00",
  "patient_age": 7,
  "limit": 10
}
```

Каждое окно содержит врача, филиал и адрес, услугу, `starts_at`, `ends_at`, часовой пояс, сведения о цене, `offer_token` и срок его действия. Общая часть ответа содержит `request_id`, актуальность, версию и признаки частичной выдачи. Сырые ответы МИС и персональные данные других пациентов наружу не выдаются.

| HTTP | Смысл |
| --- | --- |
| `200` | Результат чтения либо повтор уже завершённой операции |
| `201` | Запись подтверждена источником расписания |
| `202` | Операция принята, подтверждение ещё не установлено; возвращается `operation_id` |
| `401/403` | Нет действующего доступа / недостаточно прав |
| `404` | Объект отсутствует или не входит в разрешённую область |
| `409` | Окно занято, условия изменились либо ключ повторён с другим содержимым |
| `422` | Ошибка параметров, возрастного допуска или несопоставленные сущности |
| `429` | Ограничение нагрузки, с `Retry-After` |
| `503` | Источник недоступен до принятия операции либо расписание недостоверно |

Ошибка включает стабильный `code`, безопасное сообщение, `request_id` и рекомендации по дальнейшему действию. Неопределённость после отправки записи в 1С возвращается как статус существующей операции, чтобы клиент не создавал новую бронь.

## 8. Защита от гонок и повторов

### Обязательные гарантии

- Один медицинский ресурс не получает две подтверждённые пересекающиеся записи при вместимости один. Для групповых приёмов вместимость задаётся явно.
- Повтор одной команды возвращает исход той же операции.
- Потеря ответа не приводит к слепому повторному созданию.
- Сообщение «запись подтверждена» возникает после подтверждения источником расписания.
- Путь записи с сайта, из админки и от новых каналов использует одну политику занятости. Защита только нового эндпоинта не покрывает существующие пути.

### Протокол создания

1. Проверить доступ, лимиты, структуру и принадлежность предложения. Найти либо атомарно создать операцию по уникальному `(client_id, operation_type, idempotency_key)`. Сохранить нормализованный хэш запроса и постоянный UUID для 1С до сетевого вызова. Для хэша с персональными полями использовать HMAC с серверным секретом.
2. В короткой транзакции сериализовать проверку и резервирование ресурсов. Блокировать устойчивые строки календарных ресурсов, а не только конкретный внешний `slot_id`: разные ID могут описывать одно пересекающееся время. Для врача, кабинета и оборудования брать блокировки в фиксированном порядке. Для диапазона через полночь охватить обе даты.
3. Проверить пересечение по полуоткрытым интервалам `[start, end)`, активность, возраст, услугу и версию цены. Создать локальную запись о незавершённой операции и занятости ресурса. Зафиксировать транзакцию до HTTP-вызова.
4. Отправить в 1С сохранённый UUID. Все автоматические повторы используют его же. Установить ограниченные тайм-ауты и единственного активного исполнителя операции; срок захвата исполнителем не должен сам разрешать повтор неопределённой записи.
5. При явном успехе сохранить внешнюю запись, статус `confirmed` и событие исходящей доставки в одной локальной транзакции. При явном отказе — `rejected` и освобождение временной занятости.
6. При тайм-ауте, разрыве соединения или нераспознанном ответе — `unknown`. Сохранить историю, удержать неопределённую занятость и запустить сверку по UUID. Истечение технического TTL не является доказательством отсутствия записи.
7. Если процесс упал после успеха в 1С, но до локального сохранения, сверка должна найти бронь и завершить ту же операцию.

Локальная транзакция не объединяется в одну транзакцию с HTTP-запросом к 1С. Redis-блокировка может уменьшать конкуренцию, но корректность не должна зависеть только от её TTL. Таблицы операций и ресурсных блокировок в общей БД обеспечивают координацию нескольких экземпляров Laravel. Для SQLite требуется отдельная проверка стратегии сериализации; конкурентные приёмочные тесты проводить на целевой СУБД production.

**Окончательная защита для филиалов 1С должна быть в 1С.** Она должна атомарно проверять и занимать интервал, включая записи регистратуры и интеграций, обходящих Laravel. Локальная блокировка Laravel координирует только проходящие через него команды.

До включения записи выяснить у разработчика 1С:

- Есть ли атомарная проверка пересечений при создании, включая ручной ввод и несколько публикаций одной базы?
- Поддерживает ли создание идемпотентный `appointment_id`, как долго и в какой области уникальности?
- Как получить результат по этому UUID после потери ответа? В текущем HTTP-клиенте отдельный метод такой сверки не обнаружен.
- Какие ответы означают окончательный успех, отказ и неопределённость? Проверить legacy/manual и slot-сценарии отдельно.
- Как устроены отмена, изменение длительности, перенос и обновление расписания?

Текущий `OneCBookingService::book` допускает значения успеха по умолчанию при отсутствии отдельных полей ответа. Для нового общего ядра утвердить явные признаки подтверждения для каждой конфигурации 1С. Не считать произвольный HTTP 200 с JSON доказательством созданной записи.

Если эти гарантии отсутствуют, нужна доработка 1С. До неё канал может предлагать время и принимать заявку для ручного подтверждения с явно другим статусом. Нельзя объявлять такой режим гарантированной онлайн-записью.

## 9. Статусы, отмена и восстановление

Предлагаемая модель отделяет заявку пациента (`Application`), подтверждённую запись и операцию обмена. Существующий `Appointment` уже используется для процесса приёма — новую сущность не называть тем же именем и не подменять её назначение.

Состояния записи — `pending`, `confirmed`, `rejected`, `unknown`, `cancel_pending`, `cancel_unknown`, `cancelled`. Для операции хранить тип, попытки, UUID, клиента, время отправки, безопасную ошибку и результат. Клинические статусы посещения остаются отдельными.

Отмена использует отдельный ключ идемпотентности. До подтверждения отмены ресурс остаётся занятым. При неизвестном результате отмены выполняется сверка. Повторная отмена уже отменённой записи возвращает известный результат. Изменённый ключ или действие другого клиента не даёт права отменить чужую запись.

Право технического клиента на отмену не удостоверяет личность звонящего. Для голосовой отмены определить способ подтверждения пациента, например одноразовый код на подтверждённый контакт, либо передавать отмену оператору. Сочетание ФИО и названного телефона само по себе не разрешает чтение или изменение произвольной записи.

Перенос добавлять отдельным этапом после подтверждения контракта 1С. Если атомарный перенос отсутствует, согласовать компенсацию и поведение при частичном успехе. Автоматическая отмена старой записи перед гарантией новой недопустима.

Событие `free` без надёжной связи с записью и версии не является достаточным основанием удалить подтверждённую заявку. Текущую логику `CellsPayloadSyncService` переработать с миграцией поведения: хранить отмену и аудит, учитывать источник и область внешнего ID. Служебное ручное разрешение конфликта требует роли, причины и истории действий.

## 10. Синхронизация и очереди

Входящий webhook сначала авторизуется и сохраняется в durable inbox, затем подтверждается приём. Дедупликация — по `(connection_id, event_id)`. Если ID отсутствует, согласовать версию/последовательность; один хэш тела не позволяет отличить легитимное повторное состояние от устаревшего события.

Для расписания различать полный снимок и частичное изменение. Снимок обязательно описывает область врача/филиала и период. Отсутствующий слот можно закрыть только внутри области успешно принятого полного снимка. Частичный пакет и сбой импорта не должны очистить расписание остальных врачей.

Запоздавшее событие с меньшей версией не отменяет новое состояние. Если версий нет, конфликт с локальной подтверждённой или неопределённой операцией уходит на сверку; порядок получения запросов не доказывает порядок событий в 1С.

Изменение записи и запись сообщения в outbox выполняются в одной транзакции. Фоновый исполнитель доставляет обновление каждой подписанной площадке. Поддержать повтор с задержкой, лимиты площадки, дедупликацию, журнал доставки и очередь проблемных сообщений. Ошибка площадки не откатывает успешную запись в 1С.

Регулярная сверка проверяет зависшие операции, различия занятости и недоставленные изменения. Сроки сверки и предельный возраст расписания назначаются по измеренной частоте обновления конкретной МИС. Для первого пилота установить и проверить численные значения до активации записи.

Названия предварительные. Миграции должны быть добавочными и совместимыми с прежними клиентами.

| Сущность | Основные поля / ограничение |
| --- | --- |
| `integration_clients` / ключи | Клиент, хэш ключа, права, разрешённые филиалы, активность, ротация |

| `specialties`, `services`, предложения | Специальность, услуга, филиал, врач, возраст, длительность, цена, версия, источник |
| `booking_operations` | Клиент, тип, ключ идемпотентности, HMAC запроса, UUID 1С, запись, состояние; составная уникальность |

Существующий уникальный `(clinic_id, external_slot_id)` проверить для нескольких независимых баз и филиалов. Уникальность идентификатора слота не защищает от двух разных слотов, пересекающихся во времени.

Создание `Application` сейчас запускает model events и уведомления. При выделении общего сервиса проверить, какие события означают заявку, а какие — подтверждённую бронь. Уведомления об успешной записи отправлять после подтверждения и фиксации транзакции; повторы обработчиков не должны дублировать сообщения.

## 12. Доступ и персональные данные

Для ElevenLabs — отдельный серверный Bearer-ключ, хранение его хэша в Laravel и секрета в ElevenLabs. Права разделить на каталог/расписание, создание, чтение собственных записей и отмену. Набор филиалов проверять сервером при каждом запросе. Отсутствие настроенного ключа означает запрет доступа.

Для сайта секрет нельзя помещать в JavaScript. Его сервер может обращаться к Laravel со своим ключом, а публичная форма требует самостоятельной защиты от автоматических злоупотреблений. Прежде чем закрывать старый `POST /api/v1/applications`, обследовать все браузерные клиенты, прокси, WebApp и ботов и перевести их поэтапно. CORS и проверка `Origin` не заменяют авторизацию.

Для площадок применять подтверждённый ими протокол доступа; не предполагать, что каждая умеет Bearer. Вебхуки защищать обязательным секретом или подписью согласно контракту, с ротацией и защитой от повтора там, где протокол её поддерживает. Текущий необязательный `webhook_secret` включать после согласованного обновления отправителей.

Поиск не возвращает данные пациентов. Логи содержат `request_id`, ID клиента, операции, ресурса, статус и длительность. Телефоны, ФИО, токены и полные тела запросов маскируются. В изученном коде есть сырое логирование расписания и payload записи — включить его замену в подготовку production. Срок хранения и доступ к персональным данным согласовать с ответственным клиники, включая записи разговоров и внешнюю обработку в ElevenLabs.

## 13. Подключение ElevenLabs

### Настройка и проверка голосового поиска

1. Владелец агента даёт доступ к настройкам либо выполняет их сам. На сервере выдать отдельный ключ ElevenLabs с правами `catalog:read` и `availability:read`. В Laravel хранить хэш в `BOOKING_INTEGRATION_CLIENTS`, в ElevenLabs — полный заголовок `Bearer <ключ>` как Secret для `Authorization`. [Настройка ключа](BOOKING_INTEGRATIONS_API.md#подключение-к-тестовому-контуру).
2. Добавить в агента два Webhook Tools. Для `search_catalog` использовать `GET https://adminzrenie.ru/api/integrations/v1/catalog/search` с параметрами `type` и `q`. Для `search_slots` использовать `POST https://adminzrenie.ru/api/integrations/v1/availability/search` с JSON-фильтрами из действующего контракта. [Настройка Webhook Tools](https://elevenlabs.io/docs/eleven-agents/customization/tools/webhook-tools).
3. Настроить русский язык, часовой пояс `Europe/Moscow` и инструкцию агенту. По названиям находить ID в каталоге и уточнять неоднозначный выбор. По этим ID искать свободные окна. Озвучивать дату, время, врача и адрес из ответа. Если окон нет и `meta.empty_reason` равен `no_schedule`, сказать, что на указанные даты приёма нет. При `no_available_slots` сказать, что подходящих свободных окон нет. При `partial` или `schedule_unavailable` говорить, что расписание удалось проверить лишь частично или оно недоступно.
4. В **Test AI agent** проверить две фразы. Для «К Видлацкой сегодня или завтра, а если окон нет — ближайшее у неё» после пустого ответа `complete` искать дальше с тем же `doctor_ids` и прежними ограничениями. Для «К офтальмологу для ребёнка 7 лет в Кирове после 15:00» проверить ID города, специальность, `patient_age: 7` и `time_from: "15:01"`. Если даты не названы, уточнить нужный период. В **Call history** сверить параметры вызовов, ответы Laravel и то, какие окна озвучил агент.

### Будущий голосовой пилот с записью

Использовать Webhook Tools. MCP можно добавить как дополнительный адаптер позднее, вызывающий те же сервисы.

Настраиваемые инструменты:

1. `search_catalog` — разрешить адрес, врача, специальность и услугу в ID.
2. `search_availability` — запросить доступность по ID и датам.
3. `create_booking` — передать выбранное предложение и подтверждённые данные пациента.
4. `get_operation` — уточнить результат при `202` или потере ответа.
5. `cancel_booking` — включать после реализации проверки полномочий пациента и отмены.

В настройках каждого инструмента указать URL, метод, схему параметров и заголовок авторизации типа Secret. Установить согласованные тайм-ауты. Контекст времени передавать агенту из приложения: «25-го» и «завтра» требуют определения месяца/года и локального времени филиала.

Важное условие идемпотентности: ключ создания формируется детерминированно из ID разговора и выбранного предложения либо выдаётся сервером при выборе. Модель не должна генерировать новый случайный ключ после каждого тайм-аута. До пилота проверить реальные возможности динамических переменных ElevenLabs. При необходимости сервер связывает conversation ID и offer token в одну операцию. Повторная запись после отмены требует нового явно начатого намерения пациента.

Инструкция агенту должна требовать уточнения неоднозначного адреса/врача, озвучивания даты, филиала и известных условий, подтверждения выбора пациентом и использования только возвращённых offer token. При `slot_unavailable` повторить поиск; при `unknown` проверять ту же операцию и передавать вопрос оператору по регламенту. Не заявлять об успешной записи по одному HTTP `202`.

Окончательные настройки инструментов и JSON-схемы выпускаются из утверждённого OpenAPI после реализации. Тестировать сначала чтение расписания и сценарии в отдельной тестовой МИС, затем реальный звонок на согласованном пилоте. [Документация ElevenLabs](https://elevenlabs.io/docs/eleven-agents/customization/tools/webhook-tools).

### Текстовая проверка поиска перед подключением помощника

Для действующего API используйте [коллекцию Postman с проверками](postman/booking-integrations.postman_collection.json) и [инструкцию запуска](BOOKING_INTEGRATIONS_API.md). Этап 1 принимает специальность текстом через `specialty` и возвращает ID окна для отображения. Идентификаторы справочника специальностей и `offer_token` относятся к целевому контракту следующих этапов.

Первый этап — запустить поиск в Laravel с тестовым каталогом и расписанием и вызвать его из Postman или терминала с ключом, у которого есть права только на чтение. Запросы и ответы должны быть такими же, как у будущих инструментов агента. Для первого прогона человек сам переводит фразу пациента в параметры API. Это проверяет поиск Laravel. Разбор живой фразы проверяется отдельно при настройке агента.

Сценарий «Хочу к Видлацкой сегодня или завтра, иначе на ближайшее время» проверять с фиксированной датой 10 ноября 2026 года по часовому поясу филиала. ID и окна в сценарии тестовые.

1. Вызвать `GET /api/integrations/v1/catalog/search` с фамилией «Видлацкая». Если ответ содержит несколько врачей, уточнить имя или филиал и выбрать конкретный `doctor_id`. Дополнительно проверить поиск по форме «Видлацкой» и правила нормализации.
2. Вызвать `POST /api/integrations/v1/availability/search` с телом `{"doctor_ids":[42],"date_from":"2026-11-10","date_to":"2026-11-11","limit":5}`. Окна должны относиться к этому врачу и указанным датам, идти по времени, содержать филиал и исключать занятое и прошедшее время.
3. Если поиск вернул пустой результат по актуальному и полному расписанию, вызвать тот же маршрут с диапазоном `2026-11-12` — `2026-12-11`, тем же `doctor_id` и `limit: 1`. Ожидается ближайшее окно у того же врача в пределах диапазона. Если пациент выбрал филиал, сохранить его фильтр. Если данные неполные или устарели, показать это явно вместо вывода об отсутствии окон.

Для воспроизводимой проверки сохранить тестовый каталог, расписание, запросы и ожидаемые ответы. В каталоге нужны как минимум две клиники, два филиала одной клиники, врач в нескольких филиалах, однофамильцы и врачи с разными возрастными ограничениями. В расписании должны быть как подходящие окна, так и похожие окна, которые фильтры обязаны исключить.

| Сценарий | Ожидаемый результат |
| --- | --- |
| «Есть запись в этой клинике?» | Поиск по `clinic_ids` возвращает окна из разрешённых филиалов выбранной клиники. Филиалы другой клиники исключены. |
| «Только в Татьянином парке» или «В любом из этих двух филиалов» | Поиск по `branch_ids` возвращает окна только в указанных филиалах и показывает адрес каждого окна. Указание филиала с ID другой клиники даёт явную ошибку валидации. |
| «К Видлацкой» или «К Видлацкой либо к другому конкретному врачу» | Сначала разрешаются фамилии. При однофамильцах возвращаются кандидаты для уточнения. По выбранным `doctor_ids` выдаются окна только этих врачей, с адресом каждого приёма. |
| «На 25 ноября», «на этой неделе» или «сегодня либо завтра, иначе ближайшее» | Один день и диапазон включают только запрошенные даты. При расширении периода сохраняются врач, филиал и остальные ограничения. Прошедшие окна исключаются. |
| «На любой из этих дней с 15:00 до 18:00» | Фильтр по времени начала применяется к каждому дню в местном времени филиала. Для проверки использовать окна до диапазона, внутри него и после. |
| «К офтальмологу для ребёнка 7 лет» | Выдаются окна врачей подходящей специальности, принимающих семилетних. Проверить совпадение на границе допуска и случай, когда день рождения между двумя возможными датами приёма меняет результат. |
| «К офтальмологу для ребёнка 7 лет, в Татьянином парке, завтра с 15:00 до 18:00» | Каждое окно проходит одновременно все фильтры. Тестовые окна, отличающиеся только одним условием, исключаются. |
| «До 3 000 ₽ за конкретную услугу» — после подключения цен | Проверить точные цены ниже, ровно на границе и выше бюджета, разную цену одной услуги в двух филиалах и неизвестную цену. В выдаче остаются предложения с точной действующей ценой в пределах бюджета. Пока данных о ценах нет, поиск по расписанию доступен, а фильтр бюджета явно помечается недоступным. |
| «На завтра», когда окна заняты или расписание не обновилось | Занятые окна не выдаются. Полное актуальное расписание без окон возвращает пустой список. Устаревшие или неполные данные возвращают явный статус. |

В каждом прогоне фиксировать отправленный запрос и ответ Laravel. Голосовой поиск можно проверить через действующий API чтения. Для будущего голосового пилота с записью отдельно испытать создание записи по `offer_token` в тестовой 1С.

## 15. Этапы реализации и критерии готовности

| Этап | Работы | Критерий завершения |
| --- | --- | --- |
| 0. Контракты и исходное состояние | Инвентаризация путей записи; контракт 1С; источники цен/специальностей; тестовая МИС; базовый прогон существующих тестов | Все пути записи перечислены, ограничения 1С задокументированы, источники назначены |
| 1. Каталог и текстовая проверка поиска | Реализованы общие CatalogService и AvailabilityService, API чтения с отдельными правами, фильтры, проверка свежести ячеек 1С, демо и коллекция Postman | Демо возвращает ожидаемые окна, включая расширение периода по выбранному врачу. Перед пилотом сверить каталог и покрытие расписания на тестовой 1С |
| 2. Совместимое ядро записи | Общий BookingService, журнал операций, ресурсные проверки, сверка unknown и перевод сайта и админки на него | Старые contract tests проходят; тесты гонок и потери ответа проходят на целевой СУБД и тестовой 1С |
| 3. Защищённый API записи | Права на запись, ограничения, OpenAPI и тестовые запросы создания записи | Подтверждённый выбор окна создаёт запись в тестовой 1С; отдельный ключ отзывается без влияния на остальные каналы |
| 4. Голосовой пилот | Инструкция агенту, настройки инструментов, операторский сценарий, тестовые звонки | Подтверждение только после 1С, безопасные повторы, корректный выбор филиала/возраста/даты |
| 5. Площадки | Адаптеры по одному, mapping, экспорт, inbox/outbox, обратная сверка | Полный цикл записи и отмены проходит по контракту выбранной площадки |

Возможности включать по клиенту и филиалу. Модуль поиска поддерживает все филиалы с корректными данными; ограниченный запуск записи является этапом ввода, а не ограничением архитектуры.

Расширения БД вводить до переключения клиентов. Проверять совместное выполнение старой и новой версии на этапе выкладки. При откате отключать новые каналы, сохраняя обработку уже отправленных операций и сверку. Таблицы истории не удалять в оперативном откате. Полный откат на старый путь записи при активных `unknown` требует сверки и операционного решения.

## 16. Приёмочные проверки

- Совместимость `BookingWidgetApiContractTest`, `DoctorCalendarAvailabilityTest`, `OneCScheduleWebhookCompatibilityTest`, `AdminApplicationRoutingTest` и сценариев отмены/уведомлений. Добавить отсутствующие проверки реальных запросов внешнего `bookingApi.js`.
- Одинаковый запрос со всех каналов даёт одинаковые правила допуска и доступности при одинаковых правах и версии данных.
- Одновременные сайт, помощник, админка и площадка выбирают одно окно: ровно одна подтверждённая запись при вместимости один. Проверить и прямую запись оператором в 1С.
- Два разных slot ID и разные длительности перекрывают один ресурс: конфликт обнаружен. Непересекающиеся интервалы проходят параллельно.
- Один ключ и одинаковое тело возвращают ту же операцию; изменённое тело с тем же ключом отклоняется. Другой клиент не может прочитать её результат.
- Обрыв до отправки, после создания в 1С, после ответа и перед локальным commit; рестарт worker; исчерпание TTL. Восстановление не создаёт вторую запись.
- Запоздалое `free`, повтор webhook, частичный снимок и полный снимок другой области не освобождают чужую подтверждённую запись.
- Отмена, повтор отмены и потерянный ответ отмены корректно удерживают/освобождают ресурс.
- Поиск по возрасту на дату приёма, границам времени, разным филиалам, бюджету и неизвестной цене; устаревшее расписание даёт явный статус.
- Токены, права филиалов, лимиты, изоляция кэша, отсутствие персональных данных в выдаче и логах.
- Нагрузочная проверка широкого поиска и batch на представительном объёме. Зафиксировать p95, бюджет SQL-запросов, тайм-ауты агента/МИС и очередь доставки до допуска production.

Автоматические тесты используют изолированную БД и подменённый HTTP-транспорт. Проверка атомарности реальной 1С выполняется отдельно в согласованном тестовом контуре; mock её не доказывает. Production-записи для тестирования не создавать.

Наблюдение после запуска — доля успешных записей, конфликтов и unknown, возраст расписания, задержка синхронизации, операции без внешнего ID, ошибки доставки и сверки. Для unknown, длительно устаревшего расписания и роста ошибок определить получателя оповещения и порядок ручного разрешения.

## 17. Открытые решения до разработки

1. Конфигурации и версии баз 1С в Москве/Кирове, общность ресурсов между публикациями, атомарность записи и API проверки результата.
2. Владельцы услуг, специальностей, цен и возрастных ограничений; правила первичного/повторного приёма и длительности.
3. Нужна ли автоматическая запись голосом для филиалов `local`; по умолчанию подключать их только после реализации локальной сериализации ресурсов.
4. Полный перечень текущих клиентов публичного API и схема безопасной миграции доступа сайта.
5. Возможности ElevenLabs по conversation ID, постоянным переменным, тайм-аутам и передаче звонка оператору.
6. Порог свежести, регламент unknown и сроки хранения операций/ключей идемпотентности. Удаление старой истории не должно разрешать повтор старой команды в пределах допустимого окна повторов.
7. Контракты каждой площадки, включая доступные города, отмены, сверку и коммерческие условия.

Эти пункты ограничивают конкретные этапы. Проектировать каталог, совместимый API и тесты можно параллельно с получением ответов; включение автоматической записи зависит от доказанных гарантий источника расписания.
