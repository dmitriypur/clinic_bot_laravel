# Мониторинг онлайн-записи через 1С и Bitrix24

## Цель

Автоматически проверять работоспособность онлайн-записи через 1С и оперативно сообщать в Bitrix24 о технических ошибках реальных записей.

Старая форма записи сайта в эту задачу не входит. Изменения выполняются только в приложении `adminzrenie-laravel`.

## Согласованная архитектура

Тестовая запись проходит тем же серверным маршрутом, что и реальная заявка: локальная `Application` → существующий `OneCBookingService` → 1С → существующая отмена.

Локальная тестовая заявка создаётся с источником `monitoring`. Это позволяет сохранить `claim_id`, использовать существующую отмену и оставить заявку для ручной проверки, если отмена не сработала.

Основной сайт `zrenie.clinic` менять не требуется. Новый виджет уже отправляет заявки в API `adminzrenie`, а ошибки взаимодействия с 1С возникают и обрабатываются в этом приложении.

## Тестовая проверка

Проверка запускается ежедневно в 07:00, 12:00 и 17:00 по часовому поясу приложения `Europe/Moscow`.

Для каждого запуска:

1. Используется один контрольный филиал, заданный в конфигурации.
2. Выбирается свободный слот на период от 7 до 14 дней вперёд.
3. Создаётся локальная заявка с техническими данными пациента и `submission_source=monitoring`.
4. В запрос 1С передаётся `source=monitoring`; локальный ID заявки используется для связи логов и уведомлений.
5. Заявка отправляется через существующий механизм бронирования.
6. Полученный от 1С `claim_id` сохраняется как `external_appointment_id`.
7. Сразу вызывается существующий механизм отмены по `claim_id`.
8. После подтверждённой отмены локальная тестовая заявка удаляется.
9. В Bitrix24 отправляется результат проверки.

Тестовая заявка не должна запускать CRM-выгрузку, Telegram/SMS-уведомления пациенту или локальную аналитику реальных заявок.

Если создать запись не удалось, локальная заготовка удаляется, поскольку подтверждённой записи в 1С нет. Если запись создана, но отмена не подтверждена, локальная заявка сохраняется вместе с `claim_id` для ручной проверки и повторной отмены.

Автоматически повторять создание после таймаута нельзя: 1С могла создать запись, даже если ответ потерялся. Повторный выбор другого слота допустим только при однозначном ответе «слот уже занят».

## Требования к 1С

Новый URL и отдельный обработчик удаления не требуются.

Со стороны 1С необходимо:

- принимать и сохранять метку `source=monitoring` в обычном запросе создания;
- возвращать обычный `claim_id`;
- поддерживать текущую отмену по `claim_id`;
- освобождать слот после отмены;
- исключать отменённые записи из необходимой аналитики и выгрузок.

Физически удалять тестовые записи в 1С не нужно. Они остаются в истории со статусом «Отменена» и меткой `monitoring`.

## Уведомления Bitrix24

Для мониторинга используется отдельный входящий webhook Bitrix24 с правом `im` и отдельный групповой чат. Существующая CRM-интеграция Bitrix24 не переиспользуется, поскольку она предназначена для контактов и сделок.

Результаты тестовой проверки:

- успех создания и отмены — зелёное сообщение;
- свободный слот не найден — предупреждение «проверка не выполнена»;
- ошибка создания — красное сообщение с этапом и ответом 1С;
- создание успешно, отмена не подтверждена — критическое сообщение с локальным ID и `claim_id`;
- таймаут или неопределённый ответ — критическое сообщение без автоматического повторного создания.

Успешные реальные записи не создают служебных сообщений. При `OneCBookingException` во время реальной записи отправляется сообщение с филиалом, врачом, временем, ID заявки и технической ошибкой.

Ошибки заполнения формы, валидации и обычный конфликт занятого слота не отправляются в Bitrix24.

В уведомления нельзя включать полные ФИО, дату рождения или полный номер телефона пациента.

## Настройка

Конфигурация должна поддерживать:

- включение и быстрое отключение мониторинга;
- ID контрольного филиала;
- времена запуска `07:00,12:00,17:00`;
- границы поиска слота `7..14` дней;
- технические ФИО, телефон и дату рождения;
- базовый URL webhook Bitrix24;
- `DIALOG_ID` чата Bitrix24.

Секрет webhook хранится только в production `.env` и не коммитится.

## Обработка ошибок

Отправка сообщения в Bitrix24 не должна менять ответ API реальному пользователю. Неуспешная доставка уведомления журналируется и повторяется через очередь с ограниченным количеством попыток.

Планировщик не допускает параллельный запуск одной проверки. На production должен выполняться Laravel Scheduler.

## Проверка реализации

Необходимы автоматические тесты следующих сценариев:

- успешное создание, отмена, локальное удаление и зелёное уведомление;
- ошибка создания и красное уведомление;
- ошибка отмены, сохранение локальной заявки и критическое уведомление;
- отсутствие свободного слота;
- таймаут без повторного создания;
- реальная ошибка 1С создаёт уведомление;
- успешная реальная запись и ошибки валидации уведомлений не создают;
- ошибка Bitrix24 не влияет на ответ API пользователю;
- расписание содержит запуски в 07:00, 12:00 и 17:00.

Перед включением расписания выполняется одна ручная production-проверка: запись должна появиться в 1С с меткой `monitoring`, перейти в статус «Отменена», освободить слот и сформировать сообщение в Bitrix24.

## Вне задачи

- старая форма записи сайта;
- изменения на сайте `zrenie.clinic`;
- мониторинг недоступности `adminzrenie` из браузера;
- физическое удаление тестовых записей из 1С;
- Telegram-уведомления;
- проверка каждого филиала или каждого endpoint 1С.
