# Ручная проверка доступности записи в 1С

## Цель

Добавить на главный дашборд админ-панели кнопку, с помощью которой супер-администратор сможет вручную проверить доступность публикации 1С для записи клиентов. Результат должен сразу отображаться в админ-панели и отправляться в тот же чат Bitrix24, что и результаты проверок по расписанию.

## Границы задачи

- Кнопка доступна только супер-администратору.
- Виджет записи клиентов и его API не изменяются.
- Расписание автоматических проверок не изменяется.
- Новые таблицы и миграции базы данных не требуются.
- Проверяется существующий адрес из `BOOKING_MONITORING_URL` тем же HEAD-запросом и с теми же тайм-аутами, что и при автоматической проверке.

## Интерфейс

На странице `Dashboard` над календарями появится основное действие «Проверить доступность 1С».

- Во время запроса действие блокируется и показывает состояние загрузки средствами Filament/Livewire.
- При успешном ответе отображается зелёное уведомление с HTTP-кодом и временем ответа.
- При недоступности 1С отображается красное уведомление с понятным описанием ошибки.
- Если мониторинг выключен, запрос к 1С не выполняется и показывается предупреждение «Мониторинг отключён».
- Если автоматическая или другая ручная проверка уже выполняется, второй запрос не запускается и показывается предупреждение «Проверка уже выполняется».

Скрытие кнопки дополняется серверной проверкой роли: подделанный Livewire-запрос от пользователя без роли супер-администратора получает отказ.

## Серверная логика

Действие дашборда использует существующие `BookingAvailabilityChecker` и `BookingMonitoringNotifier`, поэтому ручная и автоматическая проверки имеют одинаковые правила определения доступности.

Перед запросом действие:

1. Проверяет роль текущего пользователя.
2. Проверяет `BOOKING_MONITORING_ENABLED`.
3. Получает существующую блокировку `booking-monitoring:availability-check`, общую с командой по расписанию.
4. Выполняет проверку и освобождает блокировку в `finally`.

В `BookingMonitoringNotifier` и фабрику сообщений добавляется отдельный сценарий ручной проверки. Сообщение в Bitrix24 явно содержит пометку «Ручная проверка», результат, HTTP-код, время ответа или безопасное техническое описание ошибки. Персональные данные клиентов в сообщение не попадают.

Отправка в Bitrix24 остаётся асинхронной через существующую очередь. Ошибка Bitrix24 не меняет результат проверки 1С и не ломает страницу дашборда; она обрабатывается существующим заданием очереди и журналированием.

## Поток выполнения

1. Супер-администратор нажимает кнопку.
2. Livewire отправляет защищённый запрос в Laravel.
3. Laravel проверяет роль, флаг мониторинга и общую блокировку.
4. `BookingAvailabilityChecker` выполняет HEAD-запрос к публикации 1С.
5. Результат ставится в очередь для отправки в Bitrix24 с пометкой о ручном запуске.
6. Filament показывает пользователю зелёное или красное уведомление.

## Обработка ошибок

- Выключенный мониторинг: предупреждение в интерфейсе, без HTTP-запроса и без Bitrix24.
- Занятая блокировка: предупреждение в интерфейсе, без повторного запроса и без Bitrix24.
- Тайм-аут, ошибка соединения или неуспешный HTTP-статус 1С: красное уведомление и сообщение об ошибке в Bitrix24.
- Ошибка постановки сообщения в очередь: проверка 1С завершается штатно, ошибка записывается в Laravel log существующим механизмом.
- Пользователь без нужной роли: HTTP 403, даже если он вручную сформировал запрос.

## Проверки

- Кнопка видна супер-администратору и скрыта от остальных ролей.
- Сервер запрещает ручной запуск пользователю без нужной роли.
- При выключенном мониторинге checker и notifier не вызываются.
- Успешная проверка показывает зелёное уведомление и ставит ручное сообщение в очередь.
- Неуспешная проверка показывает красное уведомление и ставит сообщение об ошибке в очередь.
- При занятой блокировке повторный запрос не выполняется.
- Автоматическая команда и существующие проверки по расписанию продолжают работать без изменений.
